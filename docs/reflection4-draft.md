Module 4 felt different from 1-3 — less "build the feature" and more "prove the thing you built is actually what you think it is." Half the prompts (S0, S2, S3, C2, C3, DOC3) weren't asking for code at all, just asking me to read something and either cite evidence for a claim or admit I couldn't verify it yet. That took getting used to — my instinct going in was still "execute the request," and a few times I had to catch myself and actually check something (git state, a live curl, the GitHub Actions API) instead of just answering from what I already believed to be true.

The best example of that paying off was the CI failure. The pytest -v command in the workflow was exactly what every prompt in this module specified, and it still broke on the very first push — ModuleNotFoundError: No module named 'app'. It turned out I'd been silently relying on python -m pytest out of habit through Modules 1-3, which auto-adds the working directory to sys.path; bare pytest doesn't. That bug had been sitting in the documented command the entire time and nothing local ever caught it, because CI was the first thing to actually run the command as written instead of the command I happened to type. Fixing it properly (a pytest.ini, not a workaround) and then reproducing the original failure on purpose before trusting the fix was the single most useful thing this module did for how I'd approach the next one.

The place I had to actively resist overconfidence was the Dockerfile review. I flagged two things I genuinely didn't know the answer to — whether /usr/sbin/nologin exists on python:3.11-slim, and whether a bare uvicorn CMD resolves the app package the same way python -m does — instead of asserting either way. Both turned out fine once real docker build/curl/whoami output came back, but I'd rather have flagged two questions that resolved as non-issues than have quietly assumed either one and been wrong. The DOC3 audit had a smaller version of the same lesson: my first attempt at checking the DELETE status code gave a 307, which looked like a real finding for about ten seconds until I noticed it was my own test harness passing an empty task id, not the API doing anything wrong. Almost reported a bug that was actually a bug in my checking process.

If I'm honest about what dragged, it was volume, not difficulty — sixteen prompts (S0 through X1) is a lot of sequential "check, then act, then check again," and by the CI/Docker review stretch I could feel the pull to speed-read the diff and pattern-match rather than actually trace each claim back to a line of code. The discipline this module is clearly trying to build is "mark it [VERIFY] instead of guessing" — and the one place I know I still owe that discipline something is the alpine-vs-slim question in the Dockerfile note, which I rejected on reputation and never actually benchmarked. That's the one I'd go back and close first.
